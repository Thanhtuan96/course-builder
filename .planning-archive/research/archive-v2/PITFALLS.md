# Domain Pitfalls

**Domain:** Local Web UI for CLI Tool (Express + React + SSE + WebSocket)
**Researched:** 2026-03-08
**Project:** Course Learning Plugin v2.0 - Adding Web UI to Claude Code Plugin

---

## Critical Pitfalls

### Pitfall 1: XSS via `dangerouslySetInnerHTML` in React

**What goes wrong:** The ChatPanel and LecturePanel use `dangerouslySetInnerHTML` to render Markdown content from course files and AI responses. If a malicious message or lecture content contains `<script>` tags or event handlers, they execute in the user's browser.

**Why it happens:** `marked` library parses Markdown to HTML but doesn't sanitize dangerous elements by default. Claude API responses could contain malicious payloads.

**Consequences:** 
- Session hijacking via cookie theft
- Keylogger injection
- Phishing overlays

**Prevention:**
```jsx
import DOMPurify from 'dompurify';

<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(marked(content)) }} />
```

Install: `npm install dompurify && npm install -D @types/dompurify`

**Detection:** 
- Content Security Policy (CSP) headers will block inline scripts
- Regular security audits of rendered content

**Phase:** Task 7-8 (LecturePanel + ChatPanel) — must implement before first use

### Pitfall 2: SSE Connection Limit Exhaustion

**What goes wrong:** HTTP/1.1 browsers limit SSE connections to **6 per domain**. Opening multiple tabs or retrying after errors can exhaust this limit, causing "failed to load" errors.

**Why it happens:** SSE uses long-lived HTTP connections. Each browser tab, each retry, and each reconnection counts toward the limit.

**Consequences:**
- Users can't open multiple tabs
- Automatic reconnection after network blips fails
- Web UI appears broken after brief disconnect

**Prevention:**
- Use HTTP/2 (negotiates 100 concurrent streams)
- Implement connection pooling with abort of old connections
- Add retry delay with exponential backoff

```js
// In client - SSE with retry logic
const evtSource = new EventSource('/api/chat');
evtSource.onerror = () => {
  setTimeout(() => reconnect(), Math.min(1000 * Math.pow(2, retryCount), 30000));
};
```

**Phase:** Task 4 (Chat API with SSE) — implement retry logic before UI testing

### Pitfall 3: WebSocket Broken Connections Not Detected

**What goes wrong:** The WebSocket connection for lecture refresh can break silently (network drop, server restart). The client shows stale content without any indication.

**Why it happens:** WebSocket doesn't have built-in heartbeat like TCP. Without ping/pong, dead connections appear open.

**Consequences:**
- Lecture panel shows outdated content after network issues
- User misses new sections generated by professor:next
- Confusing UX where chat works but lecture doesn't refresh

**Prevention:** Implement ping/pong heartbeat:

```js
// Server side - ws library
const interval = setInterval(() => {
  wss.clients.forEach((ws) => {
    if (ws.isAlive === false) return ws.terminate();
    ws.isAlive = false;
    ws.ping();
  });
}, 30000);

wss.on('connection', (ws) => {
  ws.isAlive = true;
  ws.on('pong', () => { ws.isAlive = true; });
});
```

**Phase:** Task 9 (WebSocket for lecture auto-refresh) — must implement heartbeat

### Pitfall 4: File System Race Conditions

**What goes wrong:** CLI commands and Web UI can read/write course files simultaneously, causing lost writes or stale reads.

**Why it happens:** Both the CLI (`professor:next`) and Web API (`/api/chat` calling Claude) write to the same `courses/{slug}/` files. No locking mechanism exists.

**Consequences:**
- Professor:next in CLI overwrites web session state
- Chat in web writes while CLI is editing
- COURSE.md progress markers lost

**Prevention:** Implement file locking:

```js
// Use proper file locking library
import lockfile from 'proper-lockfile';

async function updateLecture(slug, content) {
  const lockPath = join(coursesDir, slug, '.lock');
  await lockfile.lock(lockPath, { retries: 3 });
  try {
    // read-modify-write
    await writeFileAsync(join(coursesDir, slug, 'LECTURE.md'), content);
  } finally {
    await lockfile.unlock(lockPath);
  }
}
```

**Phase:** Task 2-4 (Course files API + Chat API) — add locking before concurrent access possible

### Pitfall 5: CLI ↔ Web UI State Desync

**What goes wrong:** Running `professor:next` in CLI updates files, but Web UI doesn't know unless WebSocket is running. Even with WebSocket, race conditions exist.

**Why it happens:** Two separate entry points (CLI and web) modify the same Markdown files without coordination.

**Consequences:**
- User in web UI sees stale lecture while CLI user progressed
- Progress tracking in COURSE.md becomes unreliable
- Confusing "which interface is correct?" user experience

**Prevention:**
- Use single source of truth with file locking (Pitfall 4)
- Broadcast ALL file changes via WebSocket, not just lecture updates
- Show "last updated by" metadata in UI

**Phase:** Task 9 (WebSocket) — needs comprehensive change notifications

## Moderate Pitfalls

### Pitfall 6: Missing CORS Configuration

**What goes wrong:** During development, Vite dev server (port 5173) calls Express API (port 3000). Without CORS, requests fail.

**Why it happens:** Different ports = different origins. Express doesn't set CORS headers by default.

**Prevention:** Already handled in implementation plan (Task 5 uses `cors` middleware). Verify it's included.

**Phase:** Task 5 (Express server) — ensure cors middleware present

### Pitfall 7: SSE Response Not Properly Closed

**What goes wrong:** If client disconnects while SSE is streaming, the server continues sending to a closed connection, causing memory leaks and "write after end" errors.

**Why it happens:** The SSE stream in `chat.js` doesn't check if response is still writable before sending.

**Prevention:**
```js
stream.on('text', (text) => {
  if (res.writableEnded) return;  // Check before writing
  res.write(`data: ${JSON.stringify({ type: 'text', text })}\n\n`);
});
```

Also handle connection abort:
```js
req.on('close', () => {
  stream.destroy();  // Cancel Claude API call
});
```

**Phase:** Task 4 (Chat API with SSE) — add connection handling

---

### Pitfall 8: No Rate Limiting on Chat API

**What goes wrong:** Users can spam the chat API, causing rapid Claude API token consumption, rate limits, and potential bill shock.

**Why it happens:** No throttling on `/api/chat` endpoint.

**Prevention:**
```js
import rateLimit from 'express-rate-limit';

const chatLimiter = rateLimit({
  windowMs: 60 * 1000, // 1 minute
  max: 10, // 10 requests per minute
  message: { error: 'Too many requests, please slow down' }
});

app.use('/api/chat', chatLimiter, chatRouter);
```

**Phase:** Task 4 (Chat API) — add before production use

### Pitfall 9: Hardcoded API Key in Client

**What goes wrong:** If using a proxy pattern, the API key might leak to client-side JavaScript.

**Why it happens:** Server-side API calls with Anthropic SDK in `chat.js` are correct. But verify Vite proxy doesn't expose secrets.

**Prevention:** Ensure proxy in `vite.config.js` only proxies to same-origin API, not external services. Already correct in plan.

**Phase:** Task 6 (React + Vite client) — verify config

---

### Pitfall 10: Memory Leak from Unclosed Streams

**What goes wrong:** Large lecture files or long conversations can cause memory pressure if streams aren't properly closed.

**Why it happens:** Express response objects and Claude SDK streams not explicitly destroyed on errors.

**Prevention:**
- Set `max_tokens` limits in Claude API calls (already in plan: 4096)
- Add cleanup in try/finally blocks
- Monitor memory in production

**Phase:** Task 4 (Chat API) — verify stream cleanup

## Minor Pitfalls

### Pitfall 11: No Graceful Server Shutdown

**What goes wrong:** `Ctrl+C` during active SSE or WebSocket connections leaves dangling handlers.

**Why it happens:** Server doesn't close connections or clear intervals on SIGTERM/SIGINT.

**Prevention:**
```js
process.on('SIGTERM', () => {
  server.close(() => {
    wss.clients.forEach(ws => ws.close());
    clearInterval(heartbeatInterval);
    process.exit(0);
  });
});
```

**Phase:** Task 5 (Express server) — add shutdown handler

---

### Pitfall 12: Missing Error Boundary in React

**What goes wrong:** Runtime errors in React components crash the entire app with white screen.

**Prevention:** Add error boundary:
```jsx
class ErrorBoundary extends React.Component {
  componentDidCatch(error, info) {
    this.setState({ hasError: true });
  }
  render() {
    if (this.state.hasError) return <div>Something went wrong</div>;
    return this.props.children;
  }
}
```

**Phase:** Task 6 (React scaffold) — add error boundary wrapper

---

### Pitfall 13: Lecture Panel Doesn't Scroll to Top on Load

**What goes wrong:** Loading new lecture content keeps old scroll position, showing empty space.

**Prevention:**
```jsx
useEffect(() => {
  if (content) {
    document.querySelector('.lecture-panel').scrollTop = 0;
  }
}, [content]);
```

**Phase:** Task 7 (LecturePanel) — add scroll reset

### Pitfall 14: Command Pills Phase Detection is Fragile

**What goes wrong:** The phase detection in ChatPanel (`if (text.includes('professor:next'))`) can match partial commands or false positives.

**Why it happens:** Simple string includes check doesn't validate command structure.

**Prevention:** Use more robust command parsing:
```js
const COMMAND_REGEX = /^professor:(next|done|hint|stuck|review|discuss|quiz)/;
const match = text.match(COMMAND_REGEX);
if (match) {
  const command = match[1];
  // Update phase based on exact command
}
```

**Phase:** Task 8 (ChatPanel) — improve command detection
