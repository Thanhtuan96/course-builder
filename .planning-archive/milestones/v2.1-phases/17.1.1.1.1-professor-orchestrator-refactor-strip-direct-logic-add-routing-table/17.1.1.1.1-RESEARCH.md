## Summary

This phase refactors the Professor agent from having direct command logic to using a declarative routing table in YAML frontmatter. The existing specialized agents (Coach, Navigator, Spotter) already handle specific commands — the work is to strip Professor of its command-specific code and make routing explicit and maintainable.

**Primary recommendation:** Migrate the existing markdown routing table (line 1142-1156 in professor.md) to YAML frontmatter, remove all Command Behaviors sections from professor.md, and keep Professor as a pure orchestrator for session start and command routing only.

### Pattern 1: YAML Frontmatter Routing

**What:** Routing table lives in YAML frontmatter of the Professor agent, parsed at runtime.

**When to use:** For all Professor commands that delegate to other agents.

**Example:**
```yaml
---
name: professor
description: >
  A Socratic teaching assistant...
routing:
  # Simple delegation - single agent
  professor:review:
    delegate_to: coach
    description: "Socratic code review with self-assessment"
  
  # Multi-step flow - sequential delegation
  professor:done:
    flow:
      - delegate_to: coach
        description: "Self-assessment gate before completion"
      - action: professor_mark_complete
        description: "Update COURSE.md, create flashcards"
      - delegate_to: navigator
        description: "Brief bridge to next section"
  
  # Internal Professor action
  professor:syllabus:
    action: read_course_file
    file: COURSE.md
    description: "Display full syllabus"
  
  # Commands Professor handles internally
  professor:new-topic:
    action: create_course
    description: "Create new course from user input"
  
  professor:hint:
    delegate_to: hint  # NEW - when hint agent exists
    # Or temporarily handled internally until agent created
    action: provide_hint_layers
    description: "Layer-by-layer hints from attempt log"
---
```

### Pattern 2: Multi-Step Flow with "then" Clauses

**What:** Declarative flow chains multiple steps with clear sequencing.

**When to use:** Commands that need multiple delegation handoffs (like `professor:done`).

**Example:**
```yaml
routing:
  professor:next:
    flow:
      - delegate_to: navigator
        description: "Bridge from previous section"
      - delegate_to: researcher
        description: "Research section content"
      - action: professor_write_lecture
        description: "Write LECTURE.md"
      - delegate_to: navigator
        description: "Bridge to current section"
```

### Pattern 3: Command File Delegation (Existing)

**What:** Command files in `commands/professor/` already specify routing.

**When to use:** This pattern already exists - commands invoke agents directly.

**Example from `commands/professor/review.md`:**
```markdown
## Route to Coach:
> "I'll hand this to Coach for review..."

Delegate to the Coach agent with:
- Current course context (from COURSE.md)
- Current section info
- User's submitted work: $ARGUMENTS
```

**Insight:** The command files already contain the delegation logic. The refactor should:
1. Keep command files as they are (or simplify them to reference routing)
2. Have Professor read its frontmatter routing table
3. Professor executes the route, not the command-specific logic in agent body

### Anti-Patterns to Avoid

- **Embedding routing in command files AND agent body:** Duplication causes drift
- **Making Professor do work after delegation:** Professor should be "dumb router" only
- **Mixing YAML frontmatter and markdown table:** Choose one format consistently
- **Removing session start logic:** Professor must still restore context on conversation start

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Agent invocation | Build custom delegation code | Use established "hand off" pattern from command files | Already proven, consistent |
| Routing logic | Parse markdown tables | Use YAML frontmatter | Machine-readable, standard format |
| Command registration | Manually edit plugin.json for each command | Keep existing plugin.json structure | Works fine, no need to change |

**Key insight:** This is a refactor, not a new feature. The delegation infrastructure already exists — we're making it explicit and maintainable.

## Common Pitfalls

### Pitfall 1: Incomplete Migration
**What goes wrong:** Some command logic remains in Professor body while other logic moves to routing.
**Why it happens:** Large file, incremental changes, missed sections.
**How to avoid:** 
- List all sections to remove BEFORE starting
- Verify each Command Behaviors section has corresponding routing entry
- Run grep for command names in Professor body after migration

### Pitfall 2: Broken Multi-Step Flows
**What goes wrong:** `professor:done` flow breaks because Professor no longer knows how to mark complete.
**Why it happens:** Professor body had the "mark complete" logic, now needs routing entry.
**How to avoid:**
- Map each Professor action in existing flows to explicit routing entries
- For internal Professor actions (like "mark complete"), create explicit action handlers

### Pitfall 3: Routing Table Syntax Errors
**What goes wrong:** YAML syntax errors break the routing table parsing.
**Why it happens:** Indentation, missing colons, incorrect nesting.
**How to avoid:**
- Use YAML linter or validate syntax before committing
- Test with simple routing entry first

### Pitfall 4: Lost Session Start Logic
**What goes wrong:** Context restoration at session start stops working.
**Why it happens:** Refactor removes too much from Professor body.
**How to avoid:**
- KEEP all Session Start and Context Restoration sections in Professor
- Professor should only lose Command Behaviors, not orchestrator logic
