## Reversibility gates

- **Gate A (helper semantics):** the helper table test must pass before any call site imports the
  helper. A wrong predicate is a security hole, not a UX bug.
- **Gate B (pairing):** run the existing legacy pairing tests plus the new bare-token cases before
  changing `applyPairingFromUrl`. Pairing rejection must be proven to leave provider, onboarding and
  storage untouched while still calling `replaceState`.
- **Gate C (storage):** prove sanitize-on-read and sanitize-on-persist with a seeded localStorage
  before wiring the use-time guards. No migration is added; rollback is a git revert.
- No database/schema change exists in this plan.

## Phase SUMMARY instructions

The executor must record these in the Phase 6 SUMMARY as known beta limitations:

- **127.0.0.2–127.255.255.254 are accepted by `isLoopbackBridgeUrl` but CSP-blocked.** The predicate
  accepts all of IPv4 `127.0.0.0/8` (D-10), while the CSP `connect-src` can only name the literal
  `127.0.0.1` (CSP has no CIDR syntax; `127.0.0.2` is not covered by `127.0.0.1`). IPv6 loopback is
  rejected by the predicate and absent from the CSP (D-22). A bridge or runner
  pinned to any other 127.x address passes the app's guard and then fails in the browser as a CSP
  violation, not as `loopback_required`. Document `localhost` or `127.0.0.1` as the recommended
  endpoints.
- The remote-adapter guard is **URL-scoped**: it rejects every `post`/`health` call whose base URL is
  non-loopback, whether or not a token is present.
- The `csp_blocked` custom-origin limitation remains a documented beta limitation; browser
  JavaScript/SQL/Python runners keep working because dedicated workers do not inherit the meta CSP.
