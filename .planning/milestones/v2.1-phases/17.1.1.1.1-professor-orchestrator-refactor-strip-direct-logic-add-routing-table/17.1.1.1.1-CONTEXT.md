# Phase 17.1.1.1.1: Professor Orchestrator Refactor - Context

**Gathered:** 2026-03-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Refactor the Professor agent to use a routing table instead of direct command logic. Strip all command-specific code from Professor and delegate to specialized agents (Coach, Spotter, Navigator) via explicit routing rules. Professor becomes a pure orchestrator.

</domain>

<decisions>
## Implementation Decisions

### Routing Table Format
- **Frontmatter:** Routing lives in YAML frontmatter of the Professor agent file
- Follows Claude Code conventions, machine-readable, easy to parse

### Delegation Scope
- **Full delegation:** Professor becomes pure orchestrator
- All commands delegate to specialized agents:
  - `professor:review` → Coach
  - `professor:done` → Coach → Professor (mark complete) → Navigator
  - `professor:stuck` → Coach
  - `professor:hint` → Hint agent (new)
  - `professor:next` → Navigator → Researcher → Professor → Navigator
  - `professor:progress` → Navigator
  - `professor:spotter` → Spotter
  - `professor:quiz` → Quiz agent (new)
  - `professor:syllabus` → Professor (reads COURSE.md)
  - `professor:new-topic` → Professor (creates course)

### Flow Handling
- **Declarative:** Routing table has "then" clauses
- Example: `review → Coach → Professor → Navigator`
- Each step clearly defined in routing config

### Professor Role
- **Orchestrator only:** 
  - Session start and context restoration
  - Command routing based on routing table
  - No command-specific logic

### Claude's Discretion
- Exact frontmatter structure
- How to handle error cases in routing
- Whether routing failures show user-friendly messages

</decisions>
